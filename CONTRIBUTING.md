# Contributing to PhairDLNA

Thank you for considering a contribution. PhairDLNA is at the requirements stage:
the specification exists, the implementation does not. Contributing to a project at
this stage is unusually welcome — the shape of the code is still being decided.

## Before you write anything

1. Read [AGENTS.md](AGENTS.md) — the binding working rules.
2. Read [WHERE_TO_CHANGE.md](WHERE_TO_CHANGE.md) — the index of the code.
3. Read the specification of the feature you want to work on:
   [docs/03-features/](docs/03-features/).
4. Read [docs/00-governance/PROJECT-STANDARDS.md](docs/00-governance/PROJECT-STANDARDS.md)
   — the code rules.

## What a contribution needs

| | |
| --- | --- |
| **A requirement** | Every behaviour change starts from a requirement ID, or a proposal for one. See [docs/00-governance/REQUIREMENTS-METHOD.md](docs/00-governance/REQUIREMENTS-METHOD.md) |
| **A specification** | If the behaviour changes, the feature specification changes with it, including its acceptance criteria |
| **Tests** | Positive, **negative**, boundary and recovery cases. A feature without a negative test is not finished |
| **Evidence** | The exact command you ran and its output. "Should work" is not evidence |
| **Documentation** | The feature specification, the getting-started guide and `WHERE_TO_CHANGE.md` where relevant |
| **A security look** | Say explicitly whether the change touches a trust boundary: the filesystem, the multicast socket, the HTTP surface, the administration surface, a parser or the supply chain |

## House rules

- **No telemetry, no analytics, no cloud dependencies, no advertising.** Ever.
- **No dependency without a licence assessment** — add it to
  [docs/04-security/DEPENDENCY-LICENSE-REVIEW.md](docs/04-security/DEPENDENCY-LICENSE-REVIEW.md).
- **No `unsafe`** without an ADR and a written safety argument.
- **No stubs presented as finished.** A function that returns a fixed value is not an
  implementation.
- **No test that is skipped or ignored to make a run green.**
- **Never publish real personal media, real file paths or private data in a fixture.**
  Test media is generated by the test.
- Keep the code small, documented and readable by a programming beginner. If a module
  cannot be explained in one sentence, split it.

## Running the gates

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
scripts/check-file-size.sh
scripts/check-doc-links.sh
python3 scripts/generate_requirement_views.py --check
```

The full list is in [docs/06-development/BUILD-AND-TEST.md](docs/06-development/BUILD-AND-TEST.md).

## Security issues

**Do not open a public issue for a vulnerability.** See [SECURITY.md](SECURITY.md).
